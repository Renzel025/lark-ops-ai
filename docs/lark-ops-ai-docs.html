P0 Session lifecycle — declare → meeting → end

The spine every other feature hangs on. A P0/P1 declaration reserves a Lark VC meeting, posts the join link, DMs duty, tracks who joins/leaves, and tears the session down on end, cancel, or the VC closing on its own — writing a log wrap-up each time.

Gotchas learned the hard way

Stale sessions block all future declares.

A natively-ended VC (no typed end/cancel) never runs delete_session, so sessions/<chat>.json lingers and the single-meeting guard rejects new declares. Aged out at P0_SESSION_DISK_MAX_AGE_HOURS (default 12), or rm the file.

Auto-cancel needs open_ids on the join event.

vc_external_join_count only increments for a join carrying an open_id ≠ trigger. A real-but-anonymous join can't stop the empty-room auto-cancel. The timer is guarded by a run_id so stale reschedules are ignored.

Cancel ≠ End.

Cancel recalls the join link everywhere + drops the deferred overview-builder DM; end flips the card to "ended" + flushes it. Both post a log wrap-up. Cancel's API force-end is opt-in (P0_VC_CANCEL_API_END_ENABLED) because tenant tokens get 99991663 — default cancel just recalls the link and lets the VC close when people leave.

Double-declare / double-end.

Dedupe at declare (_try_consume_keyword_trigger_dedupe) AND cross-process via exclusive_lock(chat_id). Cancel pre-registers _mark_meeting_cancelled so the Lark-fired meeting_ended_v1 doesn't post a redundant "ended" card over the "cancelled" one.

Source of truth: features/session/session.py. · State: P0_SESSIONS + P0_SHARED_STATE_DIR. · Deploy: git pull + systemctl restart lark-ops-ai.

Gotchas learned the hard way

The forwarder is a second Lark app.

It keeps its own token cache and must be added to the broadcast group. With no app creds it degrades to a custom-bot webhook that posts text only and returns no message_id — so broadcast edit/recall silently no-op.

try_claim_overview_send is the only double-post guard.

Under Lark's double-delivery + a double-tap, this atomic lock + immediately recording the group post id is what stops a re-post while a slow forwarder/bitable finishes.

Bitable cards can fire twice conceptually.

On P0 declare AND after overview send — deduped per session (_session_bitable_already_posted). A partial deploy/ops post is deliberately NOT marked complete so the after-overview path retries.

Draft/preview state is per operator, on disk.

Card buttons carry the oc_ scope in their value so a different replica can rebuild the preview — multi-replica deployments rely on this, not shared memory.

Orphaned drafts get retargeted.

If a draft's incident session ended, it's re-pointed to the standalone source so the operator isn't told "meeting ended" while also being told to use Build overview.

Gotchas learned the hard way

Solo reports rarely page alone.

MIN_SOLO_REPORTERS=2 — one high-confidence message won't alert unless a 2nd unique reporter hits the same fingerprint in the 60m window, or the player count is widespread. A named 1–2 players actively blocks the solo path.

Two dedupe/cooldown layers.

(a) 30s webhook re-delivery dedupe; (b) per chat:category:concern cooldown (20m). Same issue re-reported in the window is silently suppressed — the usual "why didn't it fire again."

No recipients = looks dead.

Empty P0_DM_INSTRUCTION_OPEN_IDS → classification still runs but the alert DM sends to nobody (logged as a warning).

Maintenance guard runs first.

Anything about scheduled/under/back-from maintenance is dropped before the LLM ever sees it; a negation guard also suppresses "working fine / resolved / withdrew without issue."

Detection ≠ action (by design).

Auto-detection only DMs + buzzes duty. The in-group reply, OnIt reaction, VC meeting, ring, check-person invite, and auto-overview are all downstream of a human clicking Declare as P0.

Gotchas learned the hard way

ERROR vs WARNING.

Real-time alerts only fire ≥ P0_MONITORING_LOG_MIN_LEVEL (ERROR). Many real failures log at WARNING and won't alert in real time — they only surface via the P0 session capture (P0_SESSION_LOG_MIN_LEVEL=WARNING) when those session toggles are on.

Handler level vs emit gate.

install_log_handler lowers the handler threshold to the session floor so WARNING records still reach emit() — but the ERROR gate in emit() still blocks them from the real-time alert; they're only buffered/thrown via the session path.

Shared 120s dedupe.

Identical messages (same key) are suppressed across both flows via one map — prevents floods but can hide a repeating error mid-cooldown.

Anti-loop skips.

The handler ignores uvicorn.access, its own monitoring: posts, and bitable-failure lines (dedicated path) — a post failure can't re-trigger itself. New alert paths must not emit WARNING+ from inside the post path.
